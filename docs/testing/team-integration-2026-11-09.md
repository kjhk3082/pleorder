# 팀원 소스 통합 검증 · 2026-11-09

원본 검토 기준은 [ars2323/PleOrder bb91d11](https://github.com/ars2323/PleOrder/tree/bb91d112f40657c00d9cc9ad0888ef2c59249606)이다. Kotlin 앱 전체를 복사하지 않고 대화·개인화·시간 역산·추적·투명 Activity 진입 구조를 기존 JS 주문 저장소와 Java 호스트에 이식했다. 사전 분석은 [소스 검토](../reviews/team-pleorder-2026-11-09.md)를 참고한다.

## 반영한 기능

- `FIND_FOOD`: 가게 추천 → 번호/이름 선택 → 메뉴 → 옵션 → 초안. 후보 3개, 더 보기, 상세 조회, 2분 선택 유효기간. 선택만으로 결제하지 않는다.
- `MANAGE_FOOD_ORDER`: 수량·옵션·메뉴 추가/삭제·수령 방법·요청사항 변경, 주문별 현황·번호·취소·예약 재개. 변경 시 견적을 새로 읽고 다시 승인받는다.
- 완료 주문의 메뉴·수량·옵션을 복원하는 최근 주문과 3회 이상 동일 구성의 평소 주문. 시간대·배송지·완료 횟수를 추천에 반영한다. 데모 seed·취소 주문을 이용자 완료 이력으로 세지 않는다.
- 최대 3건의 진행 주문, 화면의 주문 선택, 가게/주문 번호별 음성 조회. 여러 주문이나 명시한 대상이 모호하면 다시 묻고 다른 주문을 변경하지 않는다.
- 결제된 예약과 매장에 전송한 주문을 구분한다. 최신 차량 ETA 또는 Naver 경로의 절대 도착 시각으로 전송 시각을 계산한다. 픽업은 집이 아닌 매장까지의 경로를 사용한다.
- 차량 경로 취소/재탐색·목적지 변경·추적 공백 시 미전송 예약을 즉시 보류한다. 승인받은 배달 주소·결제 금액을 자동으로 바꾸지 않으며 명시적인 재개/취소를 받는다.
- `OrderTrackingService`가 앱 배경에서도 5초 간격으로 모의 주문을 추적하고 30초마다 차량 목적지를 재조회한다. 내비 경유지 추가는 기존 항목을 보존하고 반영 결과를 재조회한다.

## 유지한 구조

기존 글래스 UI·P 로고·Naver 지도/자동차 경로·카드 UI와 `PaymentRepository`를 유지했다. 한국 대상 `CarUxRestrictions` 처리와 별도 DO 화면도 유지했다. 외부 주문/결제 연동은 추가하지 않았고, 실제 주문·청구는 발생하지 않는다. 옵션은 명시된 데모 메뉴에만 추가했으며 실제 매장의 공식 옵션으로 표시하지 않는다.

## 발견한 오류와 수정

1. Gleo broadcast 경로에서 시작한 추적 서비스가 Android의 백그라운드 FGS 제한으로 거절됐다. 공식 스키마의 activity 진입에 투명 DO Activity를 연결하고 정상 전경 수명주기에서 추적 서비스를 시작한다. 빈 task affinity로 기존 주차 화면이 전면에 끌려오는 현상도 방지했다.
2. 배경 Gleo 저장과 숨겨진 UI의 저장이 충돌했다. 배경 차량 이벤트는 직렬화된 엔진으로 보내고, 저장 직전 상태 비교 실패 시 최신 상태로 한 번만 다시 계산한다. 기존 견적 일치·결제 멱등성 검사는 유지한다.
3. 같은 캐시 ETA를 매 프레임 다시 더하거나 이전 위치 샘플이 목적지를 덮어쓰는 문제를 수정했다. ETA와 측정 시각을 묶고 오래된 샘플을 적용 전에 거절한다.
4. 예약 결제 시점부터 매장 취소/환불 시간을 계산하던 오류를 수정했다. 실제 모의 전송 시각부터 계산한다.
5. 한국어 수량에서 `500ml`, `2인 세트`를 주문 개수로 오인하지 않도록 했다. 옵션 가격은 저장된 카탈로그로 검증하며 요청에서 받은 금액을 신뢰하지 않는다.
6. 거절이 포함된 승인 문장은 취소가 우선이다. 카드 변경 발화는 승인 값이 함께 와도 즉시 결제하지 않는다. 모호하거나 없는 주문 대상을 다른 활성 주문으로 대체하지 않는다.

## UI 확인

실제 Android WebView에서 1224×880 CSS 화면으로 확인했다. Naver 지도, 글래스 색상·여백·기존 내비게이션을 유지하면서 필요한 상태를 추가했다. 캡처는 개인정보 보호를 위해 `.cache/integration-ui/`에만 보관한다.

| Before | After | Why |
|---|---|---|
| 음성 후보가 일회성 안내에 그침 | 번호가 붙은 가게·메뉴·옵션 선택 행 | 화면과 다음 음성 선택이 같은 후보를 참조 |
| 결제와 매장 접수를 혼동하기 쉬움 | 예약 대기·보류 안내와 재개/취소 버튼 | 아직 매장에 보내지 않은 상태를 명확히 표현 |
| 진행 주문을 한 건만 표시 | 주문 선택과 주문별 상세 | 동시에 진행되는 배달·픽업 구분 |
| 새 예약 버튼 높이 43 CSS px | 최소 48 CSS px, reduced-motion 대응 | 작은 조작 영역과 불필요한 반복 모션 방지 |

## 검증 및 제한

- `npm test`: 130/130 통과. 기존 결제·지도·주소·주행 정책 회귀와 새 대화·개인화·예약 경계 사례를 포함한다.
- APK 빌드 및 emulator-5554 설치 성공. `OrderTrackingService`의 실제 foreground 실행도 확인했다.
- 음성 시험은 Windows 한국어 합성 음성을 에뮬레이터 가상 마이크에 주입한다. 실제 Gleo의 음성 인식 → 함수 선택 → 앱 처리 → Gleo 응답을 거치며, 주문 함수를 ADB로 직접 호출한 검증이 아니다.
- 각 시험은 전체 앱 상태를 로컬 백업하고 `finally`에서 복원한다. 실제 사용자의 카드·주문·장소를 테스트 데이터로 덮어둔 채 끝내지 않는다.
- 사람 목소리·호출어 감지·실차 주행·실결제 테스트는 아니다. 짧고 모호한 발화는 Gleo 자체 답변이나 재질문으로 빠질 수 있어 성공한 문장과 실패를 구분한다.
- 새 내비 경유지 보존 코드는 SDK 컴파일 및 재조회 흐름을 확인했지만, 모든 차량 내비 구현의 경유지 추가를 실차에서 검증하지 않았다.
- 사용자가 강제 종료하거나 기기를 재부팅한 뒤 앱을 다시 열기 전까지의 실행을 보장하지 않는다. 추적 공백이 90초를 넘으면 미전송 예약은 보류한다. 실제 서버 기반 예약으로 전환할 때 별도의 서버 작업 실행과 재조정이 필요하다.

주행 시험은 Virtual Console의 정상 차량 입력으로 진행했다. 콘솔 heartbeat가 중단되어 DDS가 비활성 상태인 것을 발견해 정상 세션을 연결했고, 규제 값을 수정하거나 끄지 않았다. 전체 시스템 캡처에 30km/h와 D단이 표시되며, 다른 앱을 띄운 상태에서 Gleo를 처리했다. 끝난 뒤 P단·0km/h와 원래 앱 상태를 복원했다.

짧은 “평소 먹던 거”와 “플레오더 네, …”는 Gleo가 앱 이름/발화 의도를 잘못 잡은 실행이 있었다. 전자는 “플레오더 앱에서 평소에 자주 먹던 메뉴로 새 주문을 담아 줘”, 후자는 위 표의 명확한 거절 문장으로 실제 경로를 검증했다. “네, 결제하지 마”가 앱에 도착했을 때 거절이 우선하는 로직은 별도 회귀 테스트가 통과했다. 임의 발화가 모두 인식된다고 주장하지 않는다.
