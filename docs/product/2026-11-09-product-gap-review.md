# 플레오더 제품 점검 · 2026-11-09

아래 본문은 v7 초기 점검 당시의 빈틈 목록이며, 구현 완료 목록이 아니다. 이후 변경된 상태는 아래 갱신 표를 우선한다. 실제 서비스 수준에는 여전히 파트너 API, 주소별 배달 권역, 운영/보안 검증이 필요하다.

## 같은 날 반영한 변경

| 항목 | 현재 상태 |
|---|---|
| 내비 목적지 읽기 | NaviHelper 조회·변경 수신, 사용자 수락 후 배송지 전환. 실제 에뮬레이터 Callback 확인 |
| 출발 위치 | 검색/지도에서 변경, 수동 테스트 위치와 차량 GPS를 분리. 집/이번 목적지와 독립 |
| 매장 | 서울 OSM POI 45,488건. 지역/업종 필터·중복 정리·추가 목록. 주소별 실제 배달 권역은 미확인 |
| 메뉴·리뷰 | 교촌 공식 메뉴/권장가 83개. 미확인 매장은 명시적 테스트 메뉴, 리뷰는 임의 생성하지 않음 |
| 주소 | 지도 모달/검색/읽을 수 있는 주소/상세주소 음성 입력. 저장한 집과 여행 목적지 분리 |
| 설정/시각 | 설정 화면·공식 Lucide 아이콘·라이트/다크·모션 감소·유리 질감·완료 단계/사진 |
| 한국 주행 정책 | 실제 제한 비트 적용, 0x50을 전체 잠금으로 처리하던 오류 수정. DO Activity 자격/승인은 별도 |

이하 표에서 '없음'으로 적힌 항목은 초기 점검 당시 상태다. 위 갱신 표가 없는 항목은 잔여 기획 과제로 유지한다.

## 지금 확인된 것

- 배달/픽업, 메뉴 수량, 주문 확인, 명시적 음성 승인과 슬라이드 결제.
- 준비된 카드 등록/해제/기본 카드. A 충분한 한도, B 한도 부족, C 승인 확인 후 거절.
- 실제 OSM 지도 위 가상 매장/차량/라이더, OSRM 도로 경로. 공개 데모 라우팅은 실시간 교통이 아니다.
- 주변/가는 길 추천과 최근 치킨 주문 제안. 현재 데이터는 고정된 6개 매장이므로 전국 음식점 추천이 아니다.
- 주문 상태, 지연/매장 취소/환불, 문 앞 배송 완료 시각과 샘플 증빙 사진.
- Pleos 음성/위치/경로 전송 어댑터. Gleo 함수 계약 구현과 실제 Gleo 클라우드 대화 검증은 서로 다르다.

## 1. 목적지와 여행 — 최우선

| 빈틈 | 필요한 동작 | 완료 기준 |
|---|---|---|
| 배송지 모델이 집 중심 | 집/회사/숙소/여행지/임시 장소를 같은 수령 장소 모델로 취급 | 문구·음성·경로·주문 상세 모두 선택 장소 이름 사용 |
| 차량 목적지 자동 제안 없음 | 내비 목적지를 읽고 “OO호텔 주변 음식점을 볼까요?” 제안 | 수락 전 배송지와 주문은 바뀌지 않음 |
| 목적지 변경 후 정책 없음 | 결제 전 재추천, 결제 후에는 기존 배송지를 유지하고 변경 가능 여부 안내 | 내비 변경이 이미 결제한 주문을 몰래 바꾸지 않음 |
| 호텔 수령 정보 없음 | 로비/프런트/직접 수령 선택, 숙소 정책 확인, 수령인 연락 수단 | “객실 앞 배달 가능”을 임의로 가정하지 않음 |
| 수령인과 운전자 구분 없음 | 동승자/가족/본인 수령을 선택, 별도 연락처와 요청사항 | 운전자가 호텔에 도착하지 않았어도 수령 방식이 명확 |
| 저장 주소 수정·삭제 부족 | 임시/저장 주소 구분, 명칭·핀·상세주소 편집, 현재 위치 오차 표시 | 호텔을 집으로 덮어쓰지 않고 여행 종료 후 정리 가능 |

공식 NaviHelper 3.0.5에는 `getDestinationInfo()`, `onDestinationInfo()`, `onDestinationChanged()`가 있다. `NAVI_ROUTE` 권한과 SDK 연결 후 목적지를 조회하고 변경 이벤트에 다시 조회하는 구조가 가능하다. 현재 앱의 **경로 전송**과 새로 필요한 **목적지 읽기**는 별도 기능이다. 실제 내비 앱이 전달하는 필드와 이벤트는 장치에서 검증해야 한다.

출처: [목적지 조회와 변경 이벤트](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/destinations), [권한 표](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/declaring-permissions).

## 2. 추천 — 취향보다 먼저 도착 상황

| 빈틈 | 제안 |
|---|---|
| 가까운 매장이 좋은 매장으로 간주됨 | 도로 이동 시간, 배달 가능 여부, 조리 시간, 추가 우회, 도착 시간 차이를 함께 평가 |
| 추천 이유가 약함 | “최근 두 번 주문”, “호텔까지 배달 25분”, “경로에서 추가 3분”처럼 검증된 한 가지 이유 표시 |
| 목적지 밖 결과도 목록에 남을 수 있음 | 배달 가능 지역/영업/품절을 먼저 거르고 결과 없으면 픽업 또는 반경 확대 제안 |
| “치킨” 의도가 단순함 | 최근 주문 제안 → 다른 메뉴/새 가게/가격 제한으로 수정. 추천 동의와 결제 동의를 분리 |
| 가족·여행 인원 맥락 없음 | “네 명이 먹을 저녁, 5만원 안에서”로 인원/총액/메뉴 구성 추천 |
| 싫어하는 재료·선호 식단 없음 | 사용자 명시 선호 저장, 필터 적용 이유 표시, 자동 추정은 수정 가능하게 |
| 추천을 거절해도 반복 가능 | 이번 여행만 제외/이 가게 숨기기/최근 주문 제외 기능 |
| 저장 취향과 상황 추천 구분 없음 | 평일 귀가의 재주문과 여행지 새 음식 탐색을 다르게 제안 |

## 3. 메뉴·장바구니·가격

1. **메뉴 옵션:** 사이즈, 맵기, 추가 토핑, 필수 옵션, 품절 옵션, 최대 수량을 메뉴별 데이터로 관리.
2. **메뉴 정보:** 사진 확대, 구성/양/원산지·알레르기 정보 필드, 예상 준비 시간. 없는 정보를 AI가 만들지 않음.
3. **견적 갱신:** 메뉴 가격·배달팁·할인 변경 시 차액을 보여주고 다시 승인. 최초 화면의 가격을 무조건 믿지 않음.
4. **최소 주문 금액:** 부족 금액과 추가 메뉴를 보여주되 원치 않는 자동 추가 금지.
5. **장바구니 보관:** 다른 매장으로 바꿀 때 기존 메뉴 교체 확인, 앱 복귀 시 복원, 중복 요청 방지.
6. **대체 메뉴:** 품절 시 유사 가격/구성 메뉴 제안. 금액이 같아도 고객 동의 없이 교체하지 않음.

## 4. 결제와 돈 — 최우선

1. 실제 결제 연동 시 앱이 카드번호를 직접 저장하지 않는 제공자 등록/토큰 방식. 현재 등록은 준비된 가상 카드만 사용.
2. 단순 승인/거절 외에 유효기간 만료, 분실 정지, 추가 인증, 통신 단절, 승인 결과 미확인을 서로 다른 상태로 처리.
3. 실패 후 다른 카드로 돌아갈 때 장바구니·주소·요청사항 유지. 결제 결과 미확인 동안 다른 카드 중복 승인 차단.
4. 결제 화면에 최종 수령 장소·메뉴·총액·카드를 함께 고정. 슬라이드와 음성 모두 같은 견적에 동의.
5. 전액/부분 환불, 환불 접수/처리/완료와 예상 소요를 분리. 승인 취소와 입금 완료를 같은 말로 표현하지 않음.
6. 주문별 영수증·거래번호·결제 시각·할인 상세. 재주문에 이전 카드가 해제됐다면 새 카드 선택 안내.
7. 화면을 떠나거나 앱이 종료돼도 결제 결과를 먼저 복구한 뒤 재시도 가능하게.

## 5. 배달·픽업 이후

| 상황 | 필요한 제품 동작 |
|---|---|
| 매장 접수 지연 | “결제 완료 / 매장 확인 중”을 분리, 일정 시간 이후 확인 또는 취소 경로 |
| 라이더 미배정/재배정 | 바뀐 도착 예상과 변경 이유 표시. 취소 가능 시점과 고객 선택 제공 |
| 사용자가 먼저 도착 | 로비 대기/프런트 맡기기 등 수령 방법 확인 |
| 음식이 먼저 도착 | 놓을 곳이 없으면 연락·대기·반송 절차. 무조건 배달 완료로 처리하지 않음 |
| 배달 완료 사진 오류 | 다른 문/사진 없음/사진 지연을 처리. 주문별 사진·촬영시각·전달 방식 연결 |
| 미도착·누락·오배송 | 문의 사유 선택, 해당 메뉴/금액, 사진 첨부, 접수번호, 처리 상태와 후속 답변 |
| 픽업 도착 | 매장 입구/주차/픽업대 위치, 주문번호, 수령 확인. 운전 중 누를 필요 없는 도착 안내 |
| 픽업 지연 | 보관 가능 시간·매장 연락·준비 재확인. 준비 시간이 지나도 임의 수령 완료 금지 |
| 픽업 후 여행 계속 | 매장은 경유지로만 추가하고 최종 호텔/여행지 경로 유지 |

## 6. 음성은 대화 흐름 전체를 설계

- “아까 그거 두 개”, “콜라 빼고”, “다른 데”, “내가 도착할 때쯤” 같은 앞 문맥 참조.
- 잘못 들은 메뉴·수량·목적지는 후보 한두 개로 확인. 긴 메뉴판을 음성으로 모두 읽지 않기.
- 말하는 중 끼어들기, 중지, 다시 듣기, 인식 실패 후 텍스트/화면 복구.
- 주문 전 음식/수량/수령 장소/금액/카드를 짧게 읽고 **명시적인 결제 승인**을 받기.
- 대화 중 “네”가 추천 동의인지, 결제 동의인지, 수령 확인인지 현재 질문에 묶어서 해석.
- 운전 중에는 추천 한 건과 변경 사항을 짧게, 상세 메뉴·사진·주소 편집은 정차 후.
- 앱/음악/내비 안내의 오디오 포커스와 안내 중복, 백그라운드 복귀, 세션 만료 처리.
- 실제 Gleo 대화에서 함수 선택·파라미터·취소·재질문을 검증. 로컬 규칙 엔진 성공을 Gleo 성공으로 표시하지 않기.

## 7. UI·모션·접근성

- 화면마다 하나의 중심 행동. 주문 중에는 가게 탐색보다 배송 상황, 결제 중에는 최종 확인을 우선.
- 지도에는 현재 단계에 필요한 핀만. 현 위치/목적지/라이더를 구분하고 마지막 위치 갱신 시각과 오차를 표현.
- 지도 로딩/오프라인/경로 없음/권한 거절/검색 결과 없음은 각각 다른 화면으로 복구 가능하게.
- 모션은 선택 배경 이동, 카드→상세 전환, 수량/금액 변화, 결제 체크, 단계 진행, 라이더 이동에 집중.
- 배달 완료·실패 등 중요한 상태가 작은 토스트 하나로 사라지지 않게 지속 카드에도 남기기.
- 5초 음성 예시는 듣는 중/말하는 중/승인 질문 중에는 멈추고, “결제 승인”을 유도 문구처럼 반복 노출하지 않기.
- 차량 실제 터치 크기·대비·눈부심·야간 테마·화면 비율·한글 긴 문구·접근성 읽기 순서를 검증.
- reduced-motion, 키보드, 스크린리더 검증을 별도로 수행. 스크린샷만으로 접근성 완료를 판단하지 않음.

모션 참고: [Emil Great Animations](https://emilkowal.ski/ui/great-animations), [Family / shared-layout 사례](https://animations.dev/gallery), [Motion 선택 탭](https://motion.dev/examples/js-tab-select).

## 8. 제품 운영과 개인정보

1. 운전자별 프로필, 차를 공유할 때 주소·주문·연락처 노출 제어, 로그아웃/기록 삭제.
2. 주문·결제는 서버가 확정 상태를 관리하고 앱 재설치/다른 기기/오프라인 복귀에서 동기화.
3. 결제·주문·라이더 이벤트의 지연/중복/순서 역전을 재현하는 개발자 전용 테스트 도구.
4. 오류 로그에는 주소·전화·카드 정보 최소화, 운영 지표는 인식 실패/확인 이탈/승인 실패/배송 지연을 구분.
5. 실제 제휴가 없으면 주문·사진·매장·최근 주문이 데모임을 명확히 유지. 존재하지 않는 전국 배달 데이터를 꾸미지 않음.

## 우선순위 제안

1. **목적지 모델 + 내비 목적지 읽기 + 호텔 수령:** 플레오더가 차량 앱이어야 하는 이유를 만든다.
2. **견적/승인/복구 + 대화 문맥:** 잘못된 장소나 금액으로 주문하는 실패를 막는다.
3. **도로 시간 기반 추천 + 영업·품절·옵션:** 추천을 실제 선택에 도움이 되게 한다.
4. **문의·부분 환불·픽업 도착:** 주문 뒤 문제가 생겨도 끝까지 해결하게 한다.
5. **시각/모션 완성도 + 야간/접근성:** 위 상태를 아름답고 짧고 일관되게 전달한다.

## 대표 여행 시나리오

1. 내비 목적지가 OO호텔로 변경됨 → “OO호텔 주변에서 저녁을 찾아볼까요?”
2. 사용자가 동의 → 호텔을 임시 배송지로 선택. 집 주소는 보존.
3. “치킨, 둘이 먹을 거야” → 배달 가능한 후보와 호텔 도착/음식 도착 차이 제안.
4. 로비에서 직접 수령 선택 → 연락 수단 확인 → 메뉴·금액·카드 최종 확인.
5. 슬라이드 또는 “결제 승인” → 승인/매장 접수 상태를 각각 안내.
6. 교통 지연으로 음식이 먼저 도착할 전망 → “프런트에 맡길 수 있나요?” 확인. 임의 요청 변경 금지.
7. 수령 확인 → 완료 시간과 증빙 → 문제가 있으면 해당 주문에서 문의/환불 추적.

이 흐름을 기준으로 다음 구현을 묶는다. 모든 질문을 주문 때마다 새로 묻지 않고 저장 정보와 현재 상황으로 생략하되, 장소·금액·결제 승인처럼 결과를 바꾸는 항목은 명확히 확인한다.
